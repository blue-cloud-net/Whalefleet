# 开发路线图

> 路线图以**版本里程碑**为单位组织，不绑定具体日期。严格遵循**语义化版本**（SemVer）。
>
> **唯一目标版本是 `1.0.0`**——本项目此前规划的首个对外版本是 `0.1.0`，
> 现已推迟：`0.1.0` 至 `0.19.0` 是功能迭代，`1.0.0` 才是首个对外发布的版本，
> 且必须先经过 `1.0.0-rc.N` 灰度。

---

## 版本段与发布模型

| 版本段 | 含义 | 打 tag | 推 GHCR |
|--------|------|:---:|:---:|
| `0.0.x` | **已完成的开发迭代**（0.0.1 – 0.0.15） | ❌ | ❌ |
| `0.x.0` | **功能迭代**——按模块成块交付 | ❌ 只作迭代编号 | ❌ |
| `1.0.0-rc.N` | **首个对外灰度**——只修 bug + 走完准入门槛 | ✅ | ✅ Pre-release，**不打 `latest`** |
| `1.0.0` | **首个正式版**——公开 API 冻结承诺自此生效 | ✅ | ✅ 含 `latest` |
| `1.x.y` | **修复版本**——自这一级起，小版本用于发补丁 | ✅ | ✅ |

> **为什么 0.x 完全不打 tag**：tag 是「一个已发布、可被他人引用的事实」。
> 0.x 从不对外发布，打 tag 只会制造「有 tag 却 pull 不到镜像」的误解，
> 并让 Release Please 的发布 PR 反复被提出却不该被合并。
> 0.x 的交付记录写在 [CHANGELOG.md](../CHANGELOG.md) 与本文件，正式发布时汇总进 `1.0.0` 一节。

### 版本号由谁算

不手工定版本号。Release Please 读 Conventional Commits 推导：

| 提交类型 | 版本变化 |
|---------|---------|
| `feat` | 小版本 +1（`0.1.0` → `0.2.0`） |
| `fix` | 修订号 +1 |
| `perf` / `refactor` / `docs` / `style` / `test` / `chore` / `ci` / `build` | 不触发发版 |
| `feat!` / `fix!` | 1.0.0 之前**只算小版本 +1**；1.0.0 之后才算主版本 +1 |

- **0.x 期间不细分 `0.x.y`**：开发期改动幅度大，一个迭代内混着新功能与修复是常态，
  强行按「功能版 / 修复版」切分会产出大量无实际内容的版本号。
- 突破常规的版本（`1.0.0`、`1.0.0-rc.1`）在提交信息里写一行 `Release-As: 1.0.0` 指定。
- 发布流程（何时打 tag、CHANGELOG 谁写）见 [AGENTS.md](../AGENTS.md#发布流程)。

## 进度图例与总览

> **图标约定**：版本标题与条目**首列**的图标即为其状态，全文统一。

| 图标 | 状态 | 判定口径 |
|:---:|------|----------|
| ✅ | **已完成** | 代码已合入主干，且该条目的验收标准全部通过 |
| 🚧 | **进行中** | 已开工但未闭环——本节至少一个条目尚未完成 |
| ⬜ | **未开始** | 尚未开工，条目与设计处于最终态 |
| ❌ | **明确不做** | 已判定为非目标（见文末「1.0.0 之后」） |

> **维护规则**
>
> 1. 条目级图标**只出现在「已完成」与「进行中」的版本内**；未开始的版本仅在标题标 ⬜，条目保持干净。
> 2. 子条目默认**继承父条目的图标**；只有明确标注状态时才单独覆盖。
> 3. 一个版本内**不再有任何 ⬜ 条目**时，才能把标题从 🚧 改成 ✅。
> 4. 「验收」小节是**该版本的收口清单**，只有它整体打 ✅ 才算真正交付。
> 5. **`0.x.0` 的编号即执行顺序**：迭代按编号从小到大推进，编号本身不重排。
>    反过来，某个编号尚未开工时可以整体后移（连同其后续编号一起平移），
>    但**已经开工的编号不可改**——改号会让 CHANGELOG、issue 与文档里的引用全部对不上。
> 6. 0.0.1 – 0.0.15 的迭代详情已从本文件移除，交付内容见
>    [CHANGELOG.md](../CHANGELOG.md)，设计决策见 [architecture.md](./architecture.md) 与
>    [constraints.md](./constraints.md)。`0.0.6` 是**空号**，不对应任何里程碑。
> 7. **阶段 6（`0.17.0` 起）可整体后移到 `1.0.0` 之后**：`0.1.0`–`0.16.0` 是一条完整的
>    「可发布线」，尾部三个迭代是「有余力就做」。这是保护发布节奏的**退路旋钮**，不是备选方案。
> 8. **本文件的编号会演进**：重排时必须把各处**指向未来迭代的引用**
>    （`scheduled for 0.x`、「排 0.x」这类**指针**）一并更新到新编号——留着就是错的。
>    而**已发布条目里的事实描述**（「本版交付了什么」）**不追改**：那是历史记录。

### 0.1.0 ✅ — 授权基座与 MVP 收口

**目标**：落地**带作用域的 User → Role → Permission** 授权模型——权限落在角色上、分配带主机作用域，
让角色真正参与授权判定；并修掉影响部署正确性的缺陷。

**授权基座**

- ✅ **权限目录**：静态封闭集合（**不建表**——「应用有没有某功能」是编译期事实），
  按 `domain.level` 命名，分 Global 与 Host 两类作用域。Host 域为 `host.read` / `host.admin`
  与 `container` / `image` / `network` / `volume` 各自的 read + write；
  Global 域为 `user.read` / `user.write` / `role.read` / `role.write` / `host.manage`
  / `repository.read` / `repository.write` / `audit.read`。
  `PermissionScope` **预留 Container 一档**，但本迭代只开放全局与主机两条分配路径
  （落地：`Core/Permissions/Permission.cs`，**18 项**——0.4.0 新增 `repository.read` / `repository.write`；
  目录与 `POST /admin/roles/permissions` 逐项一致有守卫测试）
- ✅ **角色携带权限**：新增 `role_permissions` 表与迁移；`Role` 实体带权限集合，
  内置角色（`admin` / `operator` / `viewer` / `auditor`）的权限集**不可修改**。
  `users.role_id` 废弃——用户 ↔ 角色改为多对多
  （落地：迁移 `0006_rbac.sql`，并有「`users` 表不再有 `role_id` 列」的断言）
- ✅ **带作用域的角色分配**：新增 `user_role_assignments`（`host_id` 可空，NULL = 全局分配）。
  全局分配的全局权限生效；主机分配只在该主机上生效，且其**全局权限被忽略**
  ——否则「把 admin 分配到某台主机」会静默变成全局提权
  （落地：`PermissionCheckerTests` 钉住两条作用域规则 + 缓存键必须带 hostId）
- ✅ **角色管理 API**：`POST /api/v1/admin/roles/{list,create,update,remove,set-default,set-permissions}`；
  删除仍有有效分配的角色返回 `1512`（须先撤销分配）
  （落地：`RoleEndpointsTests` 24 条，覆盖 1511/1512/1513/1514/1510 与幂等）
- ✅ **角色分配 API**：主机中心 `POST /api/v1/admin/hosts/{hostId}/roles/{list,assign,revoke}`
  与用户中心 `POST /api/v1/admin/users/{userId}/roles/{list,assign,revoke}`
- ✅ **鉴权解析改查库**：带作用域的分配装不进单个 JWT claim，因此授权事实改为**每次请求解析并缓存**，
  `[Authorize(Roles = …)]` 换成按权限判定的自定义 `AuthorizationHandler`，内置 `admin` 角色短路。
  JWT 里的角色名只供界面展示、不再参与判定；附带收益是角色与权限改动**即时生效**，不等 token 过期
- ✅ 新错误码：`1510` 角色不存在、`1511` 角色名已占用、`1512` 角色仍有分配、
  `1513` 内置角色受保护、`1514` 未知权限、`1515` 角色分配不存在
  （⚠️ `1514` 曾在实现里漏成 `1000`——它在五处都登记齐了，唯独抛出点没用上；
  已修并补上分流守卫：未知名 `1514`、空白项 `1000`）
- ✅ **前端**：角色管理页（角色 → 权限矩阵，内置角色只读）；用户管理与主机视图的
  「可见主机」对话框改为**角色选择器**；登录与 `auth/me` 返回 `roles` 与全局有效权限集，
  菜单与操作按钮按权限集显隐

**MVP 收口**

- ✅ **批量删除端点**：容器与镜像各一条 `batch-remove`（前端 `BatchActionBar` 已就绪，本迭代补上后端；
  **部分成功也返回 200**，逐条汇报失败）。
  ⚠️ **容器侧的那条在 `0.7.0` 移除**（改为逐条调单条 `remove`），镜像侧的保留
- ✅ **socket-proxy 写操作修复**：`docker-compose.yml` 的 `POST: 1` 与固定版本已就位（0.0.x），
  本迭代补上 `proxy` 对 `socket-proxy` 的 `depends_on`（否则启动顺序不定 → 首启探活报 `1301`）
- ✅ 反向代理示例配置：`examples/reverse-proxy/`（nginx 与 Traefik，含 TLS 与 `X-Forwarded-*`），
  `.env.example` 补 `REVERSEPROXY__*`

**验收**：

1. `viewer` 被分配到某台主机后，能看到该主机及其全部容器 / 镜像 / 卷 / 网络，
   但启停 / 删除任一资源返回 `1502`；改授 `operator` 后可写
2. 同一用户在 A 主机为 `operator`、在 B 主机为 `viewer` 时，两台主机上的操作权限**互不串味**
3. 运行时新建自定义角色并分配后，**无需重登、无需等待 token 过期**即生效
4. 新建用户自动获得默认角色（`auditor`）的全局分配
5. 把内置 `admin` 分配到某台主机后，它带来的**全局权限不生效**（主机分配只认主机域权限）
6. `socket-proxy` 模式下真的完成「创建 → 启动 → 停止 → 删除」一个 nginx 容器并拉取一个镜像

> **待手工跑的那一条**：socket-proxy 模式的「创建 → 启动 → 停止 → 删除 + 拉取镜像」
> 需要真实起一套 compose + socket-proxy 容器，属于部署验收而非 CI 能覆盖的范围。
> 其余条目（授权闭环、批量删除的 200/1404 分支、反代配置）已有集成测试与前端契约测试覆盖：
> `PermissionCheckerTests`（作用域隔离与 admin 短路）、`RoleEndpointsTests`（角色与分配端点）、
> `PermissionNamesTests`（错误码分流）、`mock-contract.spec.ts`（mock 与后端同口径）。
>
> **迁移口径**：迁移建出授权相关的两张新表并调整 `users`，**不搬运历史授权数据**——
> 0.x 从未产出正式发布，没有存量部署可搬运。迁移脚本的注释需写明这一取舍，避免后来者以为是漏写。

### 0.2.0 ✅ — Volume 与 Network

**目标**：把 Docker 主要资源类型管理补齐。

- ✅ **Volume API**：`POST /api/v1/hosts/{hostId}/volumes/{list,create,remove,batch-remove,inspect}`
- ✅ **Network API**：`POST /api/v1/hosts/{hostId}/networks/{list,create,remove,inspect}`
- ✅ 前端：两个侧边栏占位页转正（列表 / 创建 / 详情）
- ✅ 容器创建表单接入卷与网络选择

**验收**：创建具名卷并挂进容器后能读到内容；创建自定义网络并把容器接入；
两个占位页不再是预告文案。

**落地记录**：

1. **列表分页在 0.4.x 补齐**（0.2.0 交付时是与容器 / 镜像不同的「不分页」）：
   如今两种资源与容器 / 镜像同一套口径——服务端内存切片、`pageSize` 默认 20 / 上限 100、
   回显夹紧后的页码与页大小。连带修掉的两处：**占用与引用数**此前恒为空
   （用量只在 `GET /system/df` 里，`GET /volumes` 不返回 `UsageData`，且现在用 `null`
   表达「不知道」、用 `0` 表达「确实是 0」）；**卷/网络下拉框**必须显式要 `pageSize: 100`，
   否则默认 20 条会让选项悄悄缺一大截。
2. **卷的 `force` 不是「强制删除」**（实测）：只要还有容器挂着该卷，
   守护进程就拒绝，**带不带 `force` 都一样**。`force` 唯一的作用是让
   「卷不存在」变成成功（幂等）。因此二次确认里说的是「先删掉使用它的容器」，
   而不是提供���个按了也没用的开关。
3. **`Docker.DotNet.Enhanced` 的 `Volumes.RemoveAsync` 会忽略 `force` 参数**——
   实测两次调用的 HTTP 请求行完全一样（查询串里没有 `?force=`），
   而守护进程在带该参数时返回 204 而非 404。幂等语义只能在应用层自己实现。
4. **网络列表没有「容器数」**：Docker 的 `GET /networks` 不返回 `Containers`，
   只有详情接口返回。补一个恒为 0 的字段会把正在用的网络显示成「0 个容器」，
   因此服务端与 mock 都不给这个字段。
5. **内置网络是 `bridge` / `host` / `none`**：Docker 26 把 `null` 改名成 `none`，
   保护名单两个都收，旧守护进程上才拦得住。
6. **网段格式校验在本层挡**：守护进程对格式错误回 400，经翻译层归成 `1402`/500——
   「自己填的网段打错一个字符」会显示成服务端故障。在本层挡下则是 `1000`/400，
   且界面能把提示落到对应输入框。

#### 实测出来的 Docker 约束（写进代码了，写界面时还要再看一遍）

1. **`docker update --memory=0` 返回 200，但限制根本没变**。守护进程对 update 的处理是
   「字段非 0 才应用」，于是 `0` 与「不传这个字段」走同一条路。
   → `update` 把 `0` 拒为 `1000` 并提示「要取消限制必须重建」。
   **界面不能提供「取消限制」的开关**，那会是一个点了没反应又显示成功的按钮。
2. **改内存上限必须同时下发 `MemorySwap`**，否则守护进程拿容器**原有**的 swap 校验并拒绝
   （`Memory limit should be smaller than already set memoryswap limit`）。
   原值是「不限」时任何新上限都通不过——症状是「第一次改内存上限就失败」，而报错看不出缺 swap。
3. **内存下限是 6 MiB**（`6291456`），不是历史上的 4 MiB。实测 `6291455` 被拒。
   取两者中更严的 6 MiB，对新旧守护进程都成立。
4. **`on-failure` 的重试次数热更新接口处理不一致**（各 Docker 版本不同），
   因此不开放该字段，保持当前值——不给用户「改了却不生效」的错觉。
5. **追加挂载会让旧容器让位而不是删除**（改名成 `whalefleet-replaced-<短ID>`），
   因为重建失败时需要它还在。**界面必须显示这个让位容器**，否则会出现一个来历不明的容器没人敢删。

### 0.4.0 ✅ — 镜像构建与私有仓库

**目标**：支持上传 Dockerfile 构建镜像，并把镜像推到私有仓库。

- ✅ **镜像构建**：`POST /api/v1/hosts/{hostId}/images/build`
  （multipart：文件字段 `context` = 构建上下文 tar + 表单字段 `tag` / `dockerfile` /
  `buildArgs` / `labels` / `target` / `platform` / `noCache`）。
  **本版一次性返回结果**，与现有 `images/pull` 保持同一形态；进度推送随 `0.5.0` 一起改
- ✅ **仓库凭据存储**（加密落 SQLite）：AES-GCM（随机 nonce），
  密钥在数据卷下的 `repository.key`（0600），与 JWT 密钥**分开**存。
  旧部署的 `registry.key` 是它的历史名，程序仍能读，但新部署不再写它。
  响应里绝不含口令，也不含密文
- ✅ **仓库管理 API**：`POST /api/v1/admin/repositories/{list,add,remove,test}`
  （全局作用域，需 `repository.read` / `repository.write`）
- ✅ **镜像 push**：`POST /api/v1/hosts/{hostId}/images/push`
  （`repositoryId` 省略时按镜像引用里的地址段自动匹配已登记的仓库）
- ✅ **前端**：构建对话框（文件上传）、仓库配置页、镜像列表的「push」操作

**验收**：上传一个 Dockerfile 能构建出镜像；配置一个私有仓库 后能 push 成功。

**落地记录**：

1. **构建上下文只收已打包的 tar**（不收多文件再由服务端打包）：后者要在服务端实现一套
   tar 写入器并配套路径穿越防护（tar 条目名可含 `../`），而收益仅是界面少一步。
2. **构建失败有两条路径，都要归到 `1806`**：请求阶段就失败（Dockerfile 不存在、语法错到无法解析）
   由 SDK 抛异常；请求成功但构建失败（基础镜像拉不动、指令执行失败）则**错误只在进度流里**
   ——HTTP 层仍是 200。不检查进度流，「Dockerfile 语法错」会被报成「成功但什么也没产出」。
3. **构建日志回带在响应里**（最多 500 行）：构建失败时 Docker 只给一行
   `returned a non-zero code: 1`，真正的原因在上面几百行里。排错的现场在用户手里。
4. **multipart 的文件段必须带 `filename`**：ASP.NET Core 靠 Content-Disposition 里的
   `filename` 判断这一段是「文件」还是「普通表单字段」。不带 filename 时 tar 被当成普通字段，
   服务端报「context 字段是必填的」——而真实客户端（`curl -F`、浏览器 FormData）都会带。
5. **仓库地址规范化的四个落点必须一致**：存库 / 镜像引用 / Docker 的 `AuthConfig.ServerAddress` /
   按地址查配置。为此把地址抽成值对象 `RepositoryServerAddress`，规范化只发生在一个地方。
6. **别名与地址各占一个部分唯一索引**：同址尤其危险——它会让「推镜像时用哪条凭据」变成随机行为。
7. **`test` 端点用 `repository.write` 而不是 `repository.read`**：测试传的是凭据，
   能用凭据意味着能读出它。给只读角色开这道门等于让对方把口令送到任意地址上去。
8. **`repository.key` 必须随数据库一起备份**（旧部署是 `registry.key`）：漏了它，
   已保存的口令全部无法解密（表现为「认证失败」，但根因是密钥没了）。
9. **错误码段选 `1800-1899`**：`1600-1699` 已被 `0.9.0` 预留给操作审计，
   `1700-1799` 预留给 `0.11.0` 告警——本迭代不能占用别人的段。

前端落地记录：

10. **构建 / 推送请求必须放宽 30 秒超时**：`http` 实例的默认超时会在真实构建跑到
    第 30 秒时返回一个与构建无关的网络超时，用户会当成「后端挂了」，而构建其实还
    在跑。两条请求都设 `timeout: 0`。
11. **multipart 必须显式覆盖 `Content-Type`**：实例默认头是 `application/json`，
    而 axios 见到 FormData + JSON 头会 `JSON.stringify(formDataToJSON(data))`
    ——**文件被静默丢掉**，服务端只报「context 是必填的」。改成
    `multipart/form-data` 才会走 FormData 分支；浏览器随后会清掉该头自己补 boundary。
12. **仓库页用 `requiresPermission` 而不是 `requiresAdmin`**：后端这道门是
    `repository.read`，自定义角色可能只带它。用 `requiresAdmin`（管理面三项权限的
    合取）会把这类用户挡在自己的页外，比后端更严。
13. **推送对话框必须把「会不会带凭据」提前说清**：匿名推送同样是成功，光看「推送
    成功」无法区分「凭据生效了」与「这个仓库根本不要凭据」——后者往往意味着地址
    配错了（推到了一个意外的公开仓库）。多标签镜像还要提示只推第一个。
14. **前端不复刻 仓库地址解析的第二套规则**：`utils/repository-display.ts` 的
    `repositoryAddressOf` 照抄后端 `ImageReference.ExtractServerAddress`
    （首段含 `.`/`:` 或等于 `localhost` 才算主机）。两边漂移的后果是「界面说会连
    A、后端实际连 B」，而 B 才决定成败。

> 后端与前端的验收口径一致：上传一个 Dockerfile 能构建出镜像；配置一个私有
> 仓库后能 push 成功。后端另有对真实私有仓库 的推送与拉回集成测试。

#### 主机技术信息补全与纠错

- ✅ **移除主机「运行时间」**：`POST /api/v1/hosts/{hostId}/overview` 的 `startedAt` 字段
  与前端全部相关文案**一并删除**（总览长条、主机卡片、概览页信息卡、对应 i18n 词条）
  - **根因**：`/info` 的 `SystemTime` 是守护进程的**当前时间**（moby `daemon/info.go`：
    `SystemTime: time.Now().Format(time.RFC3339Nano)`，官方 API 文档写的是
    "Current system-time in RFC 3339 format with nano-seconds"），**不是启动时刻**。
    `0.0.8` 把它当启动时刻填充，前端算出「已运行 0 秒」
  - **Docker Engine API 不提供守护进程启动时刻，也不提供宿主 boot time**：
    `/info` 没有、`/version` 没有、`/events` 只是内存环形缓冲。因此这不是「映射错了字段」，
    而是**该信息根本不存在**——换任何字段都换不出真的
  - **不改口径**：把 `startedAt` 改名成 `daemonTime` 并显示绝对时刻，得到的仍是另一个假数据；
    显示成守护进程的当前时间，会让人误以为那是机器的启动时刻
  - **容器级「已运行 x」不受影响**：`inspect` 的 `State.StartedAt` 是真的启动时刻
- ✅ **daemon Info 补全**：`GET /info` 的其余字段投影进概览响应的**新 `daemon` 对象**
  （列表端点与主机离线时为 `null`，与 `counts` / `version` 同口径）
  - **系统**：`OperatingSystem` / `OsVersion` / `OsType` / `Architecture` / `KernelVersion`
  - **容量**：`CpuCount`（`NCPU`）/ `MemoryBytes`（`MemTotal`）——**静态上限，不是实时指标**，
    与本档下方「不做宿主机级实时指标」的约束同源，界面上不得标成「当前 CPU」
  - **驱动**：存储驱动（`Driver` + `DriverStatus`）/ 日志驱动 / Cgroup 驱动与版本
  - **运行时**：默认运行时 / 运行时列表 / `init` 二进制 / containerd / runc / init 三者版本
  - **插件**：volume / network / log / authorization 四类
  - **Registry**：镜像加速器 / 不安全仓库 CIDR / `IndexServerAddress`
  - **其他**：Docker 根目录 / 安全选项 / live-restore / 防火墙后端 / CDI 目录 /
    代理三项（HTTP / HTTPS / NoProxy）/ 守护进程告警
  - **代理 URL 必须遮蔽 userinfo**（`http://user:pass@host` 会把密码送进 API 响应），
    与「密码永不进日志」同源
  - **不重复** `version.os` / `version.arch`（`/version` 已给），**不返回** Swarm 相关（非目标）
  - **不新增任何 Docker 调用**：全部字段都来自已有的那次 `/info`，调用次数不变

**验收**：

1. 打开容器的指标列后，CPU / 内存 / 网络随容器实际负载变化；关闭该列后订阅被释放
2. 健康检查失败的容器在列表里一眼可见（`unhealthy`），且与「未配置健康检查」（`none`）不混淆
3. 反复重启的容器能通过 `RestartCount` 看出；被 OOM 杀掉的容器能通过 `OOMKilled` 看出
4. 手动 `stop` 的容器**不**收到异常退出通知
5. 给主机打 3 个标签，按标签过滤后只剩匹配主机；点「未分组」能筛出未分组主机
6. 总览显示的磁盘用量与 `docker system df` 一致；主机详情页能看到存储驱动与日志驱动
7. 主机概览页能看到存储驱动 / 日志驱动 / Cgroup 驱动 / 运行时 / 插件 / 镜像加速器；
   代理地址中的 userinfo 已被遮蔽
8. 主机概览页与总览长条**不再出现**「已运行 0 秒」；容器列表的「已运行 x」不受影响

> **Group 与 Tag 的职责写死**（否则两套组织方式必然打架）：
> **Group = 单一归属**（分组 + 选择与过滤边界 + 批量操作边界）；
> **Tag = 多对多自由打标**（过滤与批量选择）。
> **分组与标签都不参与授权**——授权边界只有一条，就是**带作用域的角色分配**。
>
> **不做宿主机级实时 CPU / 内存 / 网络 / 负载**：Docker Engine API **没有**宿主机级
> 指标端点——`/info` 只给 `NCPU` / `MemTotal` 这样的静态上限，`docker stats` 只针对容器。
> 用容器聚合值冒充宿主机指标，会让同一个页面出现两套口径，比不给更糟。
> 主机级实时指标因此是 **1.0.0 之后** 的事（那需要目标主机上部署 Agent）。
>
> **不做主机「运行时间」**：同一个理由的另一种形式——Docker Engine API **不提供**
> 守护进程启动时刻，也不提供宿主 boot time。`/info` 的 `SystemTime` 是**当前时间**，
> 把它当启动时刻用只会得到一个恒为 0 秒的假数据。因此本档直接**移除**该字段，
> 而不是换个口径继续显示一个假的。
>
> **不持久化历史指标**：本迭代只暴露「当下值」。历史曲线仍是非目标（那需要时序存储）。

### 0.7.0 ✅ — 批量操作与资源清理

**目标**：让「一次处理一批」与「清掉无用的」不必逐条点、也不必回 CLI。

- ✅ **容器批量启停**：前端逐条调用 `start` / `stop` / `restart` / `kill` / `pause` / `resume` / `remove`
  共七个动作，**失败项逐条带原因**（此前只列名字，用户看不出是「容器不在了」还是「端口被占」）。
  **容器侧的 `batch-remove` 端点在本档移除**（见下方「刻意的不做」）
- ✅ **容器生命周期端点**：`containers/kill`（默认 SIGKILL，可指定信号）、
  `containers/pause` / `containers/resume`、以及 `containers/recreate`（**编辑并重建**，容器 ID 会变）
- ✅ **容器详情页操作区**：详情页**自成一体**（生命周期动作 +「更多」菜单），
  不必回列表页操作；配置表单从「新建」对话框里抽成公用组件（`ContainerConfigForm`）
- ✅ **按分组批量打标 / 清标**：主机管理页多选后批量追加 / 移除标签
  （分组边界来自 `0.6.0`；后端复用 `admin/hosts/tags/*`，**零改动**）
- ✅ **镜像清理**：`images/prune`（`danglingOnly` + 可选 `label` 过滤）
- ✅ **卷清理**：`volumes/prune`（可选 `label` 过滤）
- ✅ **容器接入 / 断开网络**：`networks/connect` 与 `networks/disconnect`（**幂等**）
  （原标 `0.3.0`，已移出到本档）
- ✅ **前端**：清理入口放在镜像 / 数据卷页，**先展示将删除的清单再确认**（清理不可逆）；
  镜像页的清理入口分「悬空」与「所有未使用」两档

**验收**：

1. 选中 5 个容器批量启动，其中 1 个失败时提示里能读出**具体原因**
2. 清理悬空镜像后 `docker system df` 的可回收空间下降
3. 清理入口**必须先列清单**——不能一键点下去就删
4. 主机管理页多选后能一次给这批主机追加 / 移除标签

> **`system/prune`（一次清四类）仍是明确非目标**：它把「删多少」的决定权完全交给守护进程，
> 而本项目的界面强调「先看到再确认」。本迭代只做**资源级** prune。
>
> **本档依赖 `0.6.0`**：按分组批量操作要用的分组边界、以及清理入口要展示的
> 「将删除清单」都来自那一档。

#### 三处刻意的「不做」（与初稿不同，已确认）

1. **不做服务端批量启停端点**（初稿写了 `batch-start` / `batch-stop` / `batch-restart`）：
   启停是**幂等**操作，逐条调用的代价只是几个来回；而服务端批量端点会多出
   「请求里带哪几个 ID」「上限多少」「逐条错误码怎么排」一整套契约，
   换来的只是省几次网络往返。
   **容器侧的 `batch-remove` 端点在本档一并移除**（初稿是「批量删除仍走服务端」）：
   删除同样逐条调单条 `remove`，失败项照样逐条汇报。
   逐条调用并没有丢掉「逐条汇报失败」——那正是**前端汇总**做的事；
   而服务端批量端点的汇总结构（`requested` / `succeeded` / `failures`）
   只是**同一套语义的另一处实现**，两处并存反而多一个要同步的地方。
2. **不做跨主机批量启停 / 跨主机容器选择**：分组是**主机**的分组，
   而容器列表是单主机视图（路由 `/hosts/{hostId}/containers`）。
   要做跨主机批量启停就得先做「跨主机容器列表」，那是 `0.16.0` 的列表能力。
   因此本档的分组批量**只有打标 / 清标**这一种用法（后端零改动）。
   「组内全部容器一起停」列为明确非目标——那是一次不可撤销的大动作，
   且没有承载它的界面。
3. **不做 `dryRun`**：预览清单来自 `GET /system/df`，是**策略级**的候选；
   而守护进程在真正删除时还会跳过带挂载选项的卷、按自己的引用计数判断。
   `dryRun` 只能给出「我们自己猜的清单」，与实际删除**不是同一套判断**，
   反而会承诺一件做不到的事。预览因此只做**展示**，删除端点只负责删并回带**实际结果**。

#### 落地记录（实测出来的 Docker 语义）

1. **`POST /volumes/prune` 自 Engine API 1.42 起默认只清「匿名卷」**
   （没有名字的那些）。要清具名未使用卷必须带 `all=true`，
   否则预览列出 5 个、实删 0 个。服务端**固定下发 `all=true`**，
   让预览与实际清理是同一套口径。
2. **prune 会跳过带挂载选项的卷**（`bind` 卷）：它们其实不是本地卷，回收不了空间。
   因此界面必须写明「带挂载选项的卷不会被清理」——否则就是承诺了做不到的事。
3. **`dangling=false` 的语义是「不止悬空」**（等价 `docker image prune -a`），
   不是「只要非悬空」。界面措辞因此写成「清理所有未使用镜像」。
4. **并发 prune 回 409**（`a prune operation is already running`）→ 复用 `1404`/409，
   不落进 `1402`/500（「另一项清理正在进行中，请稍后重试」比「服务端故障」有用得多）。
5. **接入 / 断开的幂等只能自己实现**：守护进程对「容器已经在这个网络上」
   在不同版本上行为不一致（有的回 403「已接入」，有的回 404「未接入」）。
   服务端先读一次容器与网络的实际状态再决定要不要调守护进程。
   顺带一个坑：容器的 `NetworkSettings.Networks` 是**按网络名**索引的，
   而用户可能拿着网络 ID 来请求——要判断「是否已接入」必须先知道这个 ID 对应什么名字。
6. **`label` 过滤是唯一的范围收窄手段**：不带它，
   `volumes/prune` 会清掉本机**全部**未被引用的卷、`images/prune` 会清掉全部悬空镜像。
   在共享的开发机上那等于删掉别的项目的数据，因此两个端点都支持可选 `label`，
   界面放在「高级」折叠项里（默认收起）。
7. **PID 1 会忽略带默认动作的信号**（**包括 SIGTERM**）：内核对 PID 1 的默认动作是「忽略」，
   只有进程自己装了 handler 才收得到。因此 `docker kill -s SIGTERM` **可能返回成功而容器继续运行**
   （实测：`sleep` 作 PID 1 时，kill 成功、容器仍 `running`）。结论：**「命令没报错」不等于「进程死了」**——
   界面因此不把「信号已送达」写成「已终止」，而是以容器**实际状态**为准。
   要让 SIGTERM 真正生效，容器里得有 `trap "exit 0" TERM` 这样的 handler。

### 0.8.0 ✅ — exec 交互式终端

**目标**：在容器内开一个可交互的 shell。

- ✅ **新增 `POST /api/v1/hosts/{hostId}/containers/terminal-token`**：返回 5 分钟过期的独立短时 token，
  仅能用于 WebSocket 连接 `/ws/hosts/{hostId}/containers/exec`；**不继承 access token 的全 API 权限**。
  走**主机作用域**路径（而不是 `/auth/terminal-token`）：`hostId` 只出现在路径里，
  中间件顺带把「主机存在 + 看得见」校验掉
- ✅ WebSocket 端点 `/ws/hosts/{hostId}/containers/exec?token=…`（独立于 SignalR，原始双向流；
  容器与命令**绑进令牌**，查询串里不接受 `containerId` / `cmd`——否则一条为 A 容器签发的票会被拿去连 B）
- ✅ 错误码 `1104`（terminal token 无效或过期）在本版启用
- ✅ **会话留痕**：每次会话写一条 Serilog 结构化日志
  （`sessionId` / `userId` / `hostId` / 容器名 / shell / 起止时间 / 时长 / 退出码 / 结束原因）；
  **不记录按键内容与终端输出**
- ✅ 前端：容器详情页内嵌 xterm.js 终端面板（FitAddon + WebLinksAddon），懒加载成独立 chunk

**验收**：打开终端能执行 `ls` / `uname` 并看到输出；
terminal token 过期后无法重连；断开后不残留容器内进程；
每次会话在日志里留下一条带 `sessionId` 的结构化记录。

> **为什么排在审计之前**：终端能直接改生产环境，却又最容易无痕。本迭代先用 Serilog 兜住空窗，
> `0.9.0` 审计落地后**改为写审计表**（含会话起止与时长）。

#### 落地记录（实测出来的约束）

1. **terminal token 与 access token 共用签名密钥，靠 audience 隔离**——`aud` 是独立的
   `whalefleet-terminal`，而主鉴权的 `ValidAudience` 是主 audience，因此它在框架的校验阶段就被拒。
   刻意**不写**「在 `OnTokenValidated` 里比对 `typ` 再拒绝」那种代码：那正是漏判即提权的位置。
2. **`/ws` 必须排除在 `CurrentHostMiddleware` 之外**：终端请求用 terminal token 鉴权，
   在中间件眼里是**匿名**的，照常走 `host.read` 校验必然 1501——症状是「一开终端就 403/1501」，
   而终端本身完全正常。主机校验与 `container.write` 判定改由端点在内部完成。
3. **`WebSocketOptions.KeepAliveInterval` 必须小于反代的读超时**：用户盯着终端想事情时没有数据流，
   nginx 默认 `proxy_read_timeout 60s`（本项目示例给 300s）会把连接当空闲掐掉，
   症状是「终端莫名断开、重连又好了」。
4. **`MultiplexedStream` 在 TTY 模式下的读是「原始字节」**：没有 8 字节帧头，
   `ReadOutputAsync` 直接返回数据并把来源标成 stdout，因此既不用自己解帧，
   也不能假设「一次读回来是一帧」。
5. **exec 要求容器运行中，已暂停的同样不行**：暂停的容器 `Running` 仍为 true，
   但 exec 会挂在启动那一刻——界面表现为「终端空白、打字没反应」。两者都归 `1404`/409。
6. **`ExecStartContainerExecAsync` 在 4.3.3 里叫 `StartContainerExecAsync(Detach=false)`**：
   旧的 `StartWithAttachContainerExecAsync` 已不存在；`Detach=true` 只是「在后台跑起来」，
   拿不到输出也写不进 stdin。
7. **resize 是文本帧、终端数据是二进制帧**：两个方向按帧类型区分，服务端不必在字节流里猜。
   文本帧解析失败**按输入处理**（用户可能把 JSON 粘进终端）。
8. **`TERM` 必须显式注入**（`xterm-256color`）：不给时容器里的 `TERM` 往往是 `dumb`，
   `ls` 不出颜色、`top` 直接报错，而界面上看不出是环境变量没给。

### 0.11.0 ⬜ — 告警规则体系

**目标**：让平台**主动**说话——而不是等人打开页面才发现机器早就挂了。

- ⬜ **规则模型**：`alert_rules`（规则类型 / 启用 / 各级阈值 / 冷却期 / 通知渠道）+ `alert_events`
- ⬜ **三级严重度**：`info` / `warning` / `critical`，**每级阈值可配**
  （默认值参考 Portainer：CPU 95 / 85 / 70%）
- ⬜ **冷却期**：同一规则在窗口内只推一次，避免「一个容器反复重启刷满通知」
- ⬜ **内置规则**：主机离线 / **容器** CPU 使用率 / 内存使用率 / 网络流量 / **备份失败** /
  **登录失败激增（暴力破解）** / **TLS 证书即将过期**
- ⬜ **通知渠道**：Webhook（`HttpClient`，零新依赖）+ 邮件（含模板）
- ⬜ **通知中心**：顶栏铃铛 + 未读红点 + 历史列表（可搜索、可标记已读、可删除）
- ⬜ 配置键：`Alerts:*`、`Notifications:*`

**验收**：

1. 把 CPU 阈值调到 1% 后一分钟内收到一条 `warning`，**冷却期内不重复推送**
2. 停掉测试主机触发 `critical`
3. 连续 10 次错误密码触发「登录失败激增」
4. 备份脚本失败触发「备份失败」告警
5. 邮件与 Webhook 各自收到一条结构一致的载荷

> **只看实时值触发，不建历史时序库**：规则判定只需「当前值 + 窗口内计数」，不需要长期曲线，
> 与「不内置监控存储」的非目标并不冲突。
>
> **必须晚于 `0.6.0`**：阈值告警的输入就是监控与可观测性提供的指标。
>
> **渠道先做 Webhook 与邮件**：Slack / Telegram / ntfy / Discord 都是 Webhook 的变体，
> 真有用户要再加，不预建一堆适配器。

- `user_role_assignments` 增加 `container_id`（与 `host_id` 成对出现——容器 ID 只在单台守护进程内唯一），
  容器级分配复用同一张表与同一套判定，不另立模型
- 判定链路扩展到容器级：主机级分配给的是该主机的域级权限，容器级分配在其之上**再收窄**——
  两者取交集，容器级分配不会放宽主机级分配已经禁止的操作
- 授权管理 UI 细化到容器粒度；错误码 `1502`（write 权限缺失）在本版启用

**验收**：只在主机级分配了 `container.read` 的用户能看列表但不能启停容器；
追加一条容器级 `container.write` 分配后可操作该容器、且操作不到同主机的其他容器。

### 0.13.0 ⬜ — 账号、团队与安全

**目标**：把「一个人一个人地配权限」变成「一群人一次配」。

- ⬜ **团队（Team）**：新增 `teams` + `team_members` 两张表——**刻意不建 `team_role_assignments`**
- ⬜ **批量授权**：选中团队 → 一次性把「角色 + 主机 / 分组作用域」写入**每个成员**的
  `user_role_assignments`。**这是 Team 存在的意义**——没有它，Team 只是个标签
- ⬜ **成员变更后的补偿**：新成员加入后提供「同步团队权限到新成员」的动作，
  并在界面上明说「团队不是授权主体，加人不会自动继承权限」
- ⬜ **用户管理补全**：改角色、启用 / 停用、会话列表（当前有效 refresh token）、强制登出
- ⬜ **密码策略**：最小长度 / 复杂度 / 有效期可配；首次登录强制改密
- ⬜ 新错误码：`1203` 团队名已占用、`1204` 团队不存在

**验收**：

1. 建一个 Team、加 3 人，执行一次批量授权后三人**同时**获得目标主机的 `operator`
2. 停用某用户后，其**已存在的会话立即失效**（不是等 token 过期）
3. 会话列表能看到该用户当前所有有效会话，并能逐个强制登出
4. 把密码策略改为「≥12 位」后，弱密码被拒（`1202`）
5. 新建用户首次登录被要求改密

> **Team 刻意不做授权主体**：`user_role_assignments` 的主体只有 User，模型不引入第二类主体。
> 换来的是零迁移成本；代价是「加人不会自动继承权限」——用**批量授权动作**补上，
> 并在界面上说实话，而不是让人以为加进团队就自动有权限了。

### 0.14.0 ⬜ — 资源导入导出与文件浏览

**目标**：把资源搬进搬出——离线交付、迁移、排障都靠它。

- ⬜ **镜像 save / load**：导出为 tar 下载；上传 tar 导入（`docker load`）
- ⬜ **容器 export / import**：导出容器文件系统为 tar（`docker export`）；上传 tar 导入为镜像
- ⬜ **容器 commit**：把容器当前状态提交为镜像（需二次确认——它会把临时改动固化）
- ⬜ **文件浏览**：容器文件系统与卷的目录浏览；只读下载单个文件；
  **写入 / 上传只在显式确认后开放**，且默认关闭
- ⬜ **反向生成定义**：导出 Stack 为 compose YAML；导出容器为 `docker run` 命令 / compose 片段
  （Stack 部分**依赖 `0.10.0`**）
- ⬜ 大文件走流式传输与进度回报，不整块读进内存

**验收**：

1. 导出 `nginx:latest` 为 tar，再 load 回来，镜像 ID 一致
2. 导出运行中容器的文件系统，再 import 成镜像，能起一个新容器
3. 浏览卷里的文件并下载，内容与原文件一致
4. 导出的 `docker run` 命令**原样可执行**（端口、环境变量、挂载、策略都在）
5. 1 GB 级 tar 的导出过程中内存占用不随文件大小线性增长

> **容器导入导出是差异化能力**：Portainer 只提供镜像 import / export，容器侧的导出 / 导入 / commit 没有。
>
> **反向生成的「模板」口径**：本迭代只做**导出定义**（YAML / `docker run`），**不依赖模板表**——
> 真正的「应用模板」仍是 [backlog.md](./backlog.md) 里的 `B-005`。等它落地，再把「存成模板」接上。

### 0.15.0 ⬜ — 部署自动化

**目标**：让「部署」这件事被外部事件驱动，而不是靠人点。

- ⬜ **资源 Webhook**：`POST /api/v1/webhooks/{token}` 触发 Stack 重新部署或容器重建；
  支持 `?tag=<新标签>` 与 `?<VAR>=<value>` 传入变量（compose 里用 `${VAR}` 引用）
- ⬜ **Webhook 令牌**：每条 Webhook 一个独立 token（可撤销、可重置）；
  **密钥必须随库一起备份**（否则恢复后所有 Webhook 静默失效）
- ⬜ **`.env` 变量与密钥**：全局变量 + Stack 级变量；界面里以引用式注入 compose，
  **值默认遮罩**，不落进 Stack 的 YAML 正文
- ⬜ **镜像自动更新**：检测上游 digest 变化 → 按策略（仅通知 / 自动重建）处理；
  重建失败**回滚到原容器**并触发告警
- ⬜ 前端：Stack 详情页 Webhook 开关 + 复制链接；变量编辑页

**验收**：

1. 向 registry push 新镜像后，Webhook 触发 Stack 重新部署并拉取到新 tag
2. 带 `?MODE=dev` 的调用后，compose 里 `${MODE}` 解析为 `dev`
3. 变量值在界面与 API 响应里默认遮罩，不写进 Stack 的 YAML 正文
4. 自动更新：新镜像推送后自动重建；**故意做一个会启动失败的镜像，确认回滚且收到告警**
5. 恢复备份后原 Webhook 链接仍然有效（token 已被备份）

> **Webhook 在 Portainer 是商业版独占**——做出来是免费版的实打实差异点。
> **自动更新的检测逻辑落在本迭代**，`0.16.0` 只负责把它显示成列表的一列。
>
> **本档依赖 `0.10.0`**：Webhook 的作用对象是 Stack，Stack 能力先于本档交付。

### 0.18.0 ⬜ — MCP 服务器（AI 接入）

**目标**：把已有的 Docker 管理能力以 **MCP（Model Context Protocol）服务器**形态暴露给 AI 客户端
（VS Code Copilot agent mode / Claude Desktop / Copilot Studio 等），让「用自然语言查容器、启停服务」
成为一等入口。**只做服务端**——不内置 LLM，也不做对话界面。

- ⬜ **传输**：仅 **Streamable HTTP**，端点 `/mcp`（与 `/api/v1` 并列，同进程、同端口），
  由官方 C# SDK `ModelContextProtocol.AspNetCore` 承载
- ⬜ **不新增后端项目**：工具类落在 `Api/Mcp/`，与 `Controllers/` 同为**入站适配器**
- ⬜ **个人访问令牌（PAT）**：`POST /api/v1/auth/tokens/{list,create,revoke}`；
  库中只存 **Argon2id 哈希**，明文**仅在创建响应里返回一次**；可撤销、可设过期
- ⬜ **按权限过滤工具**：`tools/list` 只下发调用者确实有权限的工具，**不引入第二套授权**
- ⬜ **两道闸门**：`Mcp:AllowWrite`（默认 `false`）+ **工具组开关**（只读组 / 读写组 / 仅诊断组）
- ⬜ **环境变量值脱敏**：工具返回的容器 / 镜像配置里，`env` 的**值**默认遮蔽
  （env 常含密码与 token，这是最容易泄漏的地方）
- ⬜ **DNS-rebinding 防护**：校验 `Host` 是否在 `Mcp:AllowedHosts` 白名单内，不匹配返回 **421**
- ⬜ **错误码原样回带**：工具失败要给出 `1404` / `1502` / `1300` 这类业务错误码，
  而不是笼统的 "tool failed"
- ⬜ 新错误码：`1105` PAT 无效或已撤销、`1106` PAT 已过期、`1107` PAT 不存在、
  `1504` MCP 写工具未启用
- ⬜ 前端：全局设置新增「访问令牌」页与「MCP」集成页（端点 URL + 可复制的客户端配置片段）

**验收**：

1. VS Code Copilot agent mode 里配置 `/mcp` + PAT，能列出主机与运行中容器并给出准确回答
2. `viewer` 的 PAT 调用 `stop_container` 返回 `1502`，且该工具**不在** `tools/list` 中
3. `Mcp:AllowWrite=false` 时写工具完全不下发
4. 工具返回的容器配置里 **`env` 的值被遮蔽**，而键名保留
5. 伪造 `Host` 头请求 `/mcp` 返回 **421**
6. 撤销 PAT 后下一次调用立即 `1105`

> **Portainer 2.43 已经发布了 MCP Server**（独立容器 / `uvx` stdio / `.mcpb` 包，工具从 OpenAPI 自动生成）。
> 我们的取舍是**同进程、手写工具**——换来零额外部署形态与更精确的工具语义，代价是无法独立升级 MCP 版本。
> **env 脱敏与 DNS-rebinding 防护是从它那里学来的必补项**，不是可选项。
>
> **本迭代非目标**：stdio 传输（需要额外的可执行文件分发形态）、MCP 客户端（不在平台内跑 LLM）、
> MCP 规范里的 OAuth 2.1 授权流程（自托管场景用 PAT 覆盖）。
